# ماژول‌ها: هسته کوچک می‌ماند، بخش‌ها را پلاگین‌ها می‌سازند

وضعیت: نمونهٔ اول (`modules/mr-explainer`) کار می‌کند. این سند قرارداد است؛ هر چیز «بعداً» در آخر آمده.

## چرا

هر کس دنیای خودش را می‌خواهد: یکی ظاهر کارسرا، یکی صفحهٔ MR، یکی صفحهٔ پشتیبانی خودش. اگر هر کدام به `index.mjs` و `App.jsx` دست بزنند، هسته بزرگ می‌شود و تداخل می‌دهند. پس:

- **هسته** فقط زیرساخت مشترک است: چت، ایجنت، ابزار، گارد/ریویو، جاب، تلگرام، سکرت، موتورها.
- **ماژول** یک پوشه است (`modules/<id>/`) که ایجنت، ابزار و صفحه اضافه می‌کند و به هیچ فایل هسته دست نمی‌زند.
- **پریست** (بعداً) = ظاهر + فهرست ماژول‌های روشن + چیدمان منو برای یک نصب. کارسرا می‌شود یک پریست.

## یک ماژول چه دارد

```
modules/<id>/
  module.json     # چه چیزی اضافه می‌کند (هسته فقط این را می‌خواند تا بداند)
  server.mjs      # کد پشتش (اختیاری): export default function register(api)
```

`id` باید با نام پوشه یکی باشد (`a-z`، عدد، خط تیره). نام همه‌چیز با `id` شروع می‌شود، پس دو ماژول هم‌دیگر و هسته را نمی‌پوشانند.

### module.json

| کلید | معنی |
|---|---|
| `title`, `description`, `version` | برای صفحه و فهرست |
| `presets` | محصول‌هایی که با `MODULES` خالی این ماژول را روشن می‌کنند (`griffin`، `karsara`) |
| `builtin` | `true` = بخش خود هسته (صفحه‌اش کد هستهٔ وب است)؛ ایجنت و ابزار ندارد |
| `requires.ai` | `true` = ماژول می‌تواند با `api.complete(prompt)` یک سؤال به مدل کوچک همین نصب (همان که گفتگوها را نام‌گذاری می‌کند) بدهد: خلاصه، برچسب. متن مثل یک گفتگو از سرور بیرون می‌رود، برای همین باید اعلام شود. `""` یعنی الان هیچ حسابی جواب نمی‌دهد |
| `requires.tools` | ابزارهای هسته/بروکر که ماژول اجازهٔ صدا زدنشان را دارد (`api.call`). غیر از این‌ها رد می‌شود |
| `config[]` | `{key, description, default}`؛ تنظیم خود ماژول: روی کارتش در بازارچه ویرایش می‌شود (kv `mod:<id>:config`)، وگرنه `MOD_<ID>_<KEY>`، وگرنه پیش‌فرض (`api.config(key)`) |
| `settings` | `{config: [KEY…], flags: [flag…]}`؛ تنظیم‌های هسته (`config.mjs`) و flagهای ظاهر هر کاربر (`ui-prefs.js`) که مال این بخش‌اند. روی کارت ماژول در بازارچه می‌آیند و در تنظیمات ← پیکربندی و ظاهر دیگر نیستند |
| `agents[]` | ایجنت‌هایی که ماژول می‌سازد. `id` باید `<id>` یا `<id>-…` باشد. `tools` می‌تواند نام کوتاه ابزار خود ماژول را هم بگیرد (می‌شود `<id>_<name>`) |
| `tools[]` | `{name, risk: read|write, description}`؛ نام نهایی `<id>_<name>` (خط تیره → `_`) |
| `pages[]` | صفحه‌های سایدبار: `kind: "list"` (صفحهٔ عمومی) یا `kind: "builtin"` با `route` |

صفحهٔ `list`: `source` (نام منبع داده در `server.mjs`)، `fields[]` (`text|badge|time|link`، یکی `primary`)، `filters[]` (`text|select`)، `actions[]` (`{id, label}`). یعنی **یک ماژول بدون حتی یک خط React صفحه می‌سازد**.

### server.mjs: API ای که ماژول می‌گیرد

```js
export default function register(api) {
  api.config("KEY")                       // مقدار تنظیم
  api.kv.get/set/delete(key)              // حافظهٔ خود ماژول (کلید mod:<id>:…)
  api.migrate("1", "CREATE TABLE IF NOT EXISTS mod_<id>_x (…)")   // یک بار؛ فقط جدول mod_<id>_*
  api.db.all/get/run(sql, ...params)      // برای همان جدول‌ها
  api.complete("…")                      // یک سؤال به مدل کوچک؛ فقط اگر requires.ai باشد
  api.call("gitlab_mrs", {…})             // ابزار هسته؛ فقط اگر در requires.tools باشد
  api.source("rows", async (query) => [{ id, … }])      // داده‌ٔ صفحه؛ query = فیلترها
  api.action("explain", async ({ row }) => ({ openChat: { agent, title, text } }))
  api.tool("overview", { description, inputSchema, execute(args, { chatId }) {…} })   // ابزار ایجنت
}
```

Action سه جواب می‌تواند بدهد: `{openChat}` (مرورگر با همان API عادی چت می‌سازد و باز می‌کند؛ پس همهٔ گاردهای چت اعمال می‌شود)، `{message}` یا هیچ.

## مرزهای امنیتی (در کد، نه قول)

- ماژول‌ها **first-party**اند: کد داخل ریپو، با MR و ریویو، در همان پردازه. اجرای کد غریبه از بیرون ریپو هنوز نیست.
- ابزار `risk: "write"` در هر زنجیره‌ای که Owner شروع نکرده (همکار، جاب، همتا) از گارد تأیید Owner رد می‌شود (`verdictOf` در `guardTools`)؛ در گفتگوی خود Owner مثل بقیهٔ ابزارها آزاد است.
- ماژول فقط ابزارهایی را صدا می‌زند که در `requires.tools` گفته؛ ایجنت‌هایش فقط ابزارهایی دارند که در manifest نوشته؛ هیچ ابزار ویرایش ایجنت و هیچ گارد/سکرتی در دسترسش نیست.
- جدول فقط `mod_<id>_*` و فقط `CREATE … IF NOT EXISTS`. چیز دیگری در migrate خطای شروع است.
- `module.json` و `server.mjs` باید یکی باشند (ابزار/منبع/اکشن ثبت‌نشده یا اضافه) وگرنه همان ماژول بالا نمی‌آید. ماژول خراب گزارش و رد می‌شود؛ نصب نمی‌افتد.
- ایجنت‌های ماژول یک بار ساخته می‌شوند و بعد مال Owner‌اند؛ نسخهٔ تازهٔ ماژول ویرایش او را برنمی‌گرداند.

## بخش‌های خود گریفین هم ماژول‌اند

تلگرام، جاب، حادثه‌ها، ایجنت‌های همکاران و میز کار هرکدام یک ماژول `builtin: true` هستند (`modules/telegram` و …). صفحهٔ آن‌ها هنوز کد خود هستهٔ وب است؛ ماژول فقط می‌گوید «من هستم» و روشن/خاموش‌شدنش را ممکن می‌کند (آیتم منو، تنظیمات ← ظاهر، و خود صفحه). ایجنت و ابزار ندارند.

| ماژول | پیش‌فرض گریفین | پیش‌فرض کارسرا | توضیح |
|---|---|---|---|
| `telegram` | روشن | روشن | همان بخش، دو حالت با پیکربندی: چت مادر هر همکار (`TELEGRAM_DM_MODE=assistant`، با Owner همان نصب) یا صندوق تلگرام کارسرا (`inbox`، با Owner آن نصب؛ `GRIFFIN_OWNER_*`). هر نصب Owner خودش را دارد |
| `jobs` | روشن | روشن | |
| `incidents` | روشن | روشن | |
| `peers` | روشن | روشن | «ایجنت‌های همکاران» در منو دیده می‌شود (پیش‌فرض هر دو پوسته) |
| `workbench` | روشن | روشن | |
| `mr-explainer` | روشن | خاموش | |

## روشن کردن

کلید `MODULES` (تنظیمات ← پیکربندی، یا `GRIFFIN_MODULES`):

- خالی یا `default`: پیش‌فرض محصول، یعنی هر ماژولی که در `presets` خودش اسم این محصول (`griffin` یا `karsara`) را دارد.
- `all`: همه. `a,b`: دقیقاً همین‌ها.
- `default,-jobs,+mr-explainer`: پیش‌فرض، بدون جاب، با مرج ریکوئست‌ها.

بعد از ری‌استارت اعمال می‌شود؛ روشن و خاموش‌کردن روزمره از بازارچه است (بخش پایین). پوشهٔ ماژول‌ها `modules/` در ریپو است (`GRIFFIN_MODULES_DIR`). `GET /api/modules` ماژول‌های روشن را می‌دهد و علت خطای ماژول خراب را. یک ماژول خاموش: منو و تنظیمات ظاهرش را ندارد و صفحه‌اش می‌گوید «در این نصب روشن نیست». آیتم‌های منو را هم هر کاربر با «ظاهر» می‌تواند پنهان کند.

## بازارچه: روشن، خاموش و جابه‌جا کردن، با تعارض و مهاجرت

تنظیمات ← «بازارچه» (اولین مورد منوی تنظیمات؛ از «بیشتر» سایدبار هم می‌رسد) همهٔ ماژول‌های نصب‌شده را در قفسه‌های دسته‌بندی‌شده نشان می‌دهد (چه می‌افزایند، وضعیت، خطا) و هر کدام یک کلید دارد. **همهٔ تنظیمات یک بخش روی کارت خودش است** («تنظیمات»): آمدن صفحه‌هایش در منوی کناری، flagهای ظاهری‌اش، تنظیم‌های هسته‌ای که در `settings.config` گفته (همان `PATCH /api/config`) و تنظیم خودش (`PATCH /api/modules/:id/config`). `GET /api/config` برای هر تنظیمی که مال ماژولی است `modules` را می‌گوید و صفحهٔ پیکربندی آن‌ها را نشان نمی‌دهد (`MODULES` و هر کلید `sets` هم مال بازارچه است). کلید فوری کار نمی‌کند: اول سرور می‌گوید چه می‌شود (`POST /api/modules/:id/plan`)، کاربر می‌خواند، و با «انجام بده» اعمال می‌شود (`POST /api/modules/:id/switch`). بدون ری‌استارت؛ انتخاب در kv `modules:overrides` می‌ماند و روی `MODULES` و پریست مقدم است.

در `module.json`:

- `provides: ["telegram-dm"]` — جایگاهی که ماژول پر می‌کند. هر جایگاه یک فراهم‌کننده دارد؛ دو ماژول با یک جایگاه هم‌جایگزین‌اند: روشن‌کردن یکی، دیگری را خاموش می‌کند (جابه‌جایی، نه خطا).
- `conflicts: ["id"]` — ماژولی که به هر دلیل دیگر با آن در یک نصب نمی‌شود.
- `requires.modules: ["id"]` — ماژولی که باید روشن باشد؛ با روشن‌شدن این، آن هم روشن می‌شود، و با خاموش‌شدن آن، این هم خاموش می‌شود. اگر نصب نباشد یا با انتخاب ناسازگار باشد، تغییر رد می‌شود و دلیلش گفته می‌شود.
- `sets: {KEY: "value"}` — مقداری از پیکربندی که این ماژول است (مثلاً هر روش تلگرام یک مقدار `TELEGRAM_DM_MODE` است). روشن‌شدن ماژول آن را می‌نویسد؛ موقع شروع، ماژولی که مقدارش با تنظیم زنده می‌خواند روشن است، پس بازارچه هرگز با آنچه واقعاً اجرا می‌شود نمی‌خواند. اگر تنظیم را جدا دست بزنند، بازارچه «با این ماژول نمی‌خواند» می‌گوید و «درست کن» دارد.
- `switchNote` — توضیح چیزی که با روشن‌شدن عوض می‌شود. ماژولی که note دارد به چیزی زنده وصل است (حساب تلگرام، وب‌هوک)، پس تغییرش `confirm: true` می‌خواهد (وگرنه ۴۰۹).

مهاجرت گفتگوها: چتی که صفحهٔ یک ماژول باز کرده است `chats.module` می‌گیرد. با خاموش‌شدن ماژول، این چت‌ها (بایگانی‌شده‌ها هم) به پوشه‌ای در فهرست گفتگوهای عادی به نام «ماژول <عنوان>» می‌روند (مثلاً «ماژول مرج ریکوئست‌ها»؛ `chat_groups` موجود)؛ جای قبلی هر چت یادآوری می‌شود. با روشن‌شدن دوباره، فقط چتی که هنوز در همان پوشه است به جای قبلی‌اش برمی‌گردد (چتی که کاربر جای دیگر برده همان‌جا می‌ماند) و پوشهٔ خالی‌شده پاک می‌شود. هیچ چیز پاک نمی‌شود: نه گفتگو، نه جدول‌های `mod_<id>_*`، نه ایجنت‌های ماژول.

تلگرام: دو ماژول هم‌جایگزین `telegram` (دستیار به جای شما، چت مادر) و `telegram-inbox` (صندوق، مثل کارسرا) هستند که `TELEGRAM_DM_MODE` را می‌نویسند؛ جابه‌جایی‌شان از بازارچه است و تأیید می‌خواهد.

## مسیر کوچک‌شدن هسته (چه شد، چه می‌ماند)

۱. ✅ قرارداد، لودر، صفحهٔ list عمومی، `mr-explainer`، و بخش‌های موجود به‌عنوان ماژول `builtin` با پیش‌فرض هر محصول و روشن/خاموش.
۲. ⏳ **کد سرور هر بخش داخل ماژول خودش**: الان `index.mjs` همه را می‌سازد و مسیرهایشان (`/api/telegram/*`، `/api/jobs/*`، `/api/incidents/*`، `/api/peers/*`) همیشه هست؛ ماژول خاموش فقط UI را می‌بندد. هر بخش به‌ترتیب (peers، jobs، incidents، آخر تلگرام که بزرگ‌ترین و پرتداخل‌ترین است) به `modules/<id>/server.mjs` با `register(api)` منتقل می‌شود تا ماژول خاموش واقعاً چیزی بالا نیاورد (مثلاً intake حادثه‌ها، poll تلگرام). هر انتقال یک MR جدا با تست رفتار قبلی.
۳. ⏳ صفحهٔ وب هر بخش هم به `modules/<id>/web/` برود (مثل `view` صفحه‌های list، هنگام build لود شود) تا `App.jsx` و `Sidebar.jsx` از فهرست ماژول‌ها خالی شوند.
۴. ⏳ پریست کامل: یک فایل با ظاهر + ماژول‌ها + flagها؛ کارسرا و گریفین دو پریست.

## صفحهٔ اختصاصی یک ماژول (`view`)

فهرست عمومی برای شروع کافی است، ولی هر داده‌ای شکل خودش را می‌خواهد. صفحهٔ `list` می‌تواند `"view": "<نام>"` داشته باشد؛ آن‌وقت وب به‌جای فهرست عمومی `modules/<id>/web/<نام>.jsx` را نشان می‌دهد (هنگام build پیدا و فقط با باز شدن صفحه بار می‌شود). داده، اکشن‌ها و گاردها همان صفحهٔ list است: `source` و `actions` ماژول، فقط شکل نمایش عوض می‌شود. اگر فایل در آن build نباشد، همان فهرست عمومی می‌آید.

- کامپوننت پیش‌فرض‌صادرشده `{ mod, page, onBack }` می‌گیرد.
- از هستهٔ وب فقط `@griffin/module-kit` را import کند: `useRows`، `runAction` (چت را از API معمولی چت می‌سازد و باز می‌کند)، `chatExists`، `memory` (حافظهٔ کوچک ماژول در مرورگر)، `clockLabel`/`exactTime`، `textDir`، `toast`، `navigate`. بقیهٔ فایل‌های وب مال ماژول نیست.
- منبع یک صفحه می‌تواند به‌جای آرایه `{ rows, meta }` برگرداند؛ `meta` (مثلاً «چرا فهرست خالی است») به `useRows` می‌رسد.
- ماژولی که باید کلید یک سرور MCP صاحب نصب را بخواند، اسم آن سرور را در `requires.mcp` می‌گوید و با `api.mcpServer(name)` (`{url, headers}`) روی سرور می‌خواند؛ سرور اعلام‌نشده = خطا موقع بار شدن.
- منطق خالص را در یک فایل `.js` کنارش بگذار تا تست شود (نمونه: `modules/mr-explainer/web/view.js` و `apps/web/test/mr-board.test.mjs`).
- کلاس‌های Tailwind فایل‌های `modules/*/web/*.jsx` اسکن می‌شوند.

نمونه: `mr-explainer` با `view: "board"`: کاشی‌های «نیاز به رسیدگی / آمادهٔ مرج / …» با شمارش، یک کارت برای هر MR با نوع تغییر به فارسی، دلیل وضعیت و یک دکمه؛ گفتگوی توضیح قبلی هر MR دوباره باز می‌شود.

## ساختن یک ماژول جدید

۱. `modules/<id>/module.json` + `server.mjs` را بنویس، شاخهٔ خودت، MR.
۲. اگر ابزار بروکر تازه لازم است (مثل `gitlab_mrs` برای MR)، آن هم در همان MR و فقط‌خواندنی.
۳. تست: `apps/server/test/modules.test.mjs` را الگو بگیر (host با `callTool` جعلی).
۴. بدون دست زدن به `index.mjs`، `App.jsx`، `Sidebar.jsx`.

نمونه‌ها:

- **mr-explainer**: منبع داده از `gitlab_mrs`، دکمهٔ «توضیح بده» که چت با ایجنت خودش باز می‌کند، ابزار `mr_explainer_overview`.

## هنوز نیست (به‌ترتیب)

1. **ریویوی دوگانه برای ابزار write ماژول**: الان فقط تأیید Owner دارد؛ `review.mjs changeOf` باید verdict ماژول را هم بشناسد.
2. **پریست کامل**: الان `presets` فقط می‌گوید کدام ماژول‌ها پیش‌فرض روشن‌اند؛ ظاهر و flagها هنوز در `ui-prefs.js` هستند.
4. **دسترسی به‌ازای کاربر** در نصب مشترک (الان هر نصب صاحب خودش است و ماژول روشن/خاموش per نصب).
5. **جاب و تریگر ماژول** در manifest (الان ماژول از ابزارهای جاب هسته استفاده می‌کند).
6. **ماژول بیرون از ریپو** (`<data>/modules`) با sandbox؛ تا قرارداد جا نیفتاده نمی‌کنیم.
